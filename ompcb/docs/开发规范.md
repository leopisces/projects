# OMPCB 开发规范（AI-Native SDLC）

> 本规范依据 Anthropic 官方《The AI-native SDLC playbook》梳理，针对 **OMPCB 单开发者、单仓库、小规模** 场景做了裁剪与落地化改造。
> 原则：**代码不是瓶颈，围绕代码的流程才是。让流程与 agent 产出同速，人留在判断层。**
>
> 适用对象：本项目的一切 AI 辅助开发（Claude Code / 任何 agent）与手工开发。AI 与人工遵守同一套流程。

---

## 0. 为什么需要这套流程

传统 SDLC 的每个阶段（规划/设计/构建/测试/部署/维护）由不同角色通过文档、工单、签字交接。这套流程在"写代码最贵"的时代是合理的，但现在：

- 代码生成已经很快，**瓶颈转移到构建两侧**：规划、评审/测试、部署，这些仍然以人类速度运行
- 人工逐行 review agent 写的 diff 跟不上产出速度
- 治理靠"习惯"而非"代码"，人一忙就漏

**AI-native SDLC 的回答**：把流程改成**证据闭环** —— 每个阶段产出一个可提交、可评审的 artifact（文件/记录），下一个阶段**读它启动**。提交链就是审计链。

```
intent.md →(接受)→ spec.md →(批准)→ plan.md →(实施)→ diff+测试 →(评审)→ 上线 →(监控异常)→ 新的 intent.md
```

**OMPCB 的定位**：这是单人本地工具（无鉴权、内网自用），所以这里不引入企业级的东西（分支保护、发布经理、托管 settings 等），只保留**对单人开发同样有价值的部分**：先意图后编码、写计划再动手、自检反馈闭环、知识文件化、经验回流。轻，但完整。

---

## 1. 六个阶段总览

| 阶段 | 产出 artifact | 谁触发 | 谁评审 |
|------|--------------|--------|--------|
| Plan 规划 | `intent.md` | 想法/工单/事故 | 你（产品负责人） |
| Design 设计 | `spec.md` | `intent.md` 被接受 | 你 |
| Build 构建 | `plan.md` + 代码 + 测试 | `spec.md` 被批准 | 你（agent 先自检） |
| Test 测试 | 测试/构建通过记录 | 每次改动 | 你 + 自动化 |
| Deploy 部署 | 发布记录 | 测试通过 | 你 |
| Maintain 维护 | incident 记录 → 新 `intent.md` | 线上异常 | 你 |

每阶段结束**必须提交 artifact 到 git**，下一阶段从它开始。不要跳过。

## 2. Stage 1 — Plan：先把意图写下来

**目标**：想法不再等"有人写文档"，一次说清"要什么、为什么、在什么约束下"。

### 做法

1. 有想法（功能/修复/优化）→ 先和 AI 头脑风暴，用大白话描述：
   - 现在做不了什么 / 哪里疼
   - 谁受影响
   - 更好的样子是什么
   - 哪些明确不做（范围外）
2. 让 AI 追问（分析师会问的问题）：范围、用户、约束、成功长什么样。
3. 让 AI 按下方模板生成 `intent.md`。
4. 检查 AI 理解是否偏差，修正。
5. **提交 `intent.md` 到 git**（放 `docs/intent/` 目录）。

### intent.md 模板

```markdown
# Intent: <一句话描述>

Author: <你的名字>. Status: draft.
日期: yyyy-MM-dd

## Problem
<现状痛点，越具体越好>

## Proposed outcome
<完成后是什么样>

## Affected users and systems
<影响的用户 / 文件 / 模块>

## Constraints
<硬约束：不做什么、不能破坏什么、性能要求等>

## Open questions
<未决问题，留待设计阶段回答>
```

### 验收

- 从"有想法"到"提交 intent.md"应在 **半天内**（原多周需求提炼流程压缩到小时级）
- 提交后由你（产品负责人）决定：接受进入设计 / 关闭

---

## 3. Stage 2 — Design：需求与设计合成一次会话

**目标**：把 `intent.md` 变成工程可执行的 `spec.md`，**政策在设计时就生效，而不是几周后评审才发现**。

### 做法

1. 打开新会话，把 `intent.md` 给 AI，要求产出 `spec.md`，并**点名约束、要求标注冲突点**。
2. 标准提示词：

   ```
   读取附件 intent.md，为它在本项目中的落地产出需求与设计规格 spec.md。
   应用项目已有规范（见 docs/ 下的规范文档），使方案符合本项目约定。
   明确列出任何 concern，尤其是无法同时满足的冲突约束。
   ```

3. 你评审 spec：它解决了 stated problem 吗？intent 里的 open questions 回答了吗？
4. **先处理 flagged concerns**（这是分析师本该升级的点），每个 concern 指定 owner（往往是你自己）。
5. 提交 `spec.md`（放 `docs/specs/`），与 `intent.md` 成对留存。
6. 你决定是否进入构建。高风险改动咨询技术判断后由你拍板。

### spec.md 模板

```markdown
# Spec: <名称>
> 源自 intent.md: <提交 SHA 或文件名>
日期: yyyy-MM-dd

## Requirements
- R1. <编号需求，可被计划与评审引用>
- R2. ...

## Design
- <端到端设计：数据、接口、页面、算法>
- <改动涉及的文件>

## How each intent constraint is met
| 约束 | 如何满足 |
|------|---------|
| <intent 里的约束> | <设计中的对应> |

## Open questions
<intent 未决问题的答案，或继续carry forward>

## Areas of concern
1. <冲突点/风险> Owner: <人>
```

### 验收

- 从 intent.md 提交到 spec.md 提交的耗时，应显著短于旧的"需求+设计"流程
- 需求返工：spec.md 在 plan.md 之后的改动越少越好

## 4. Stage 3 — Build：先计划，后实现

**目标**：没有批准的 `plan.md` 就不动手写代码。机构知识变成 agent 读的文件，护栏是代码而不是习惯。

### 4.1 默认从计划模式开始

1. 新会话从 **plan mode** 开始（agent 只读，不写文件）。
2. 把 `intent.md` + `spec.md` 给 agent，要一份实现计划：改哪些文件、顺序、用什么测试证明。
3. **盘问计划**：这会破坏什么？哪步最险？有哪些方案 agent 没选？
4. 迭代直到"一个没看过对话的人也能照 plan 独立实现"。
5. 提交 `plan.md`（放 `docs/plans/`）。
6. 接受计划，让 agent 实现。计划扎实时实现通常一遍过。
7. **实现偏离计划时，同一次提交里更新 `plan.md`**。

### plan.md 模板

```markdown
# Plan: <名称>
> 源自 spec.md: <文件名>
日期: yyyy-MM-dd

## Files that change
- <新文件>
- <修改文件>

## Order of work
1. ...
2. ...

## Risks
<什么可能坏，如何缓解>

## Proof
<哪些测试/验证证明完成>
```

### 4.2 CLAUDE.md：团队约定文件（本项目单人也是"团队"）

`CLAUDE.md` 给 agent 一个新加入者需要的上下文：命令、约定、架构、常犯的错。

1. 用 `/init` 让 agent 从仓库生成初版。
2. 精简到一页：构建/测试/lint 命令、重要的约定、**agent 老犯的错**。
3. 提交到 git 根目录，全项目共享一份，改动像代码一样被评审。
4. **黄金规则：agent 同一个错误犯两次 → 写进 CLAUDE.md。**

CLAUDE.md 骨架：

```markdown
# OMPCB

## Commands
- Dev: npm run dev（API 4000 + 前端 5173）
- Test: npm test（node:test，跑在临时库，不碰真实数据）
- Build: npm run build
- Seed: npm run seed（破坏性！清空 materials 重导入）

## Conventions
- 金额永远用 decimal（本项目 SQLite 用 REAL 需注意精度）
- <其他本项目约定>

## Architecture
- server/ Express + better-sqlite3；web/ Vue 3 + Vite
- 数据文件 data/ompcb.db 不入库（gitignore）

## Things Claude gets wrong
- <踩过的坑>
```

### 4.3 Skills：机构知识技能化

规则：**必须一致执行的机构知识写成 skill；属于 CLAUDE.md 或提示词的内容不要写成 skill。**

本项目可用场景示例：
- `.claude/skills/` 目录放 `SKILL.md`，frontmatter 写触发条件，正文写该怎么做
- 例：`api-convention`（接口命名/校验约定）、`db-schema-rule`（SQLite schema 变更必须幂等 + PRAGMA 自查）、`bom-display-rule`（BOM 显示口径：绑定行四列紫字、缺料橙字等——这些正是本项目反复强调的约定）

```markdown
---
name: api-convention
description: 新增/修改 /api/* 端点时应用。涉及路由、出入库接口时使用。
---
# API 约定
1. 前缀 /api。开发时 Vite 代理到 localhost:4000。
2. 库存只能经 POST /inventory/:id/move 变动，不接受直接写 stock。
3. 错误返回格式：<约定格式>
```

> **Skill 是建议性控制**：让 agent 大概率遵守，但不强制。必须恒成立的政策需要更确定性的兜底（见 4.4）。

### 4.4 Hooks：构建期护栏

Skill 是软的，Hook 是硬的。hook 在每次匹配到动作时确定性执行：

- 阻止编辑受保护路径（如 `data/`、生成文件）
- 文件编辑后自动跑 formatter/linter，防止漂移积累
- 防止凭据进入 diff

> ⚠️ **要人批准的 hook 属于 Deploy 阶段**（见 Stage 5）。构建期 hook 只做自动化的 allow/block，**不要**在构建期弹人工审批 —— 那会把开发者拉回关键路径。

本项目现阶段（单人、无 CI）建议 hook 从最轻的开始：**阻止编辑 `data/` 数据库文件 + 提交前跑测试**。配置在 `.claude/settings.json`（如使用 Claude Code）或项目 scripts。

### 4.5 并行与子代理（可选，单人也可用）

- 需要同时做几件不碰同一批文件的事 → 各自开 session（git worktree 隔离）
- 反复出现的工作 → 定义子代理（`.claude/agents/`），如 verifier（跑 app 验证行为）、researcher（探索代码不刷屏）

## 5. Stage 4 — Test：自检反馈闭环 + 持续评估

**目标**：agent 在人看到之前自己验证并修好自己。人看的时候已经是"通过检查"的产物。

### 5.1 Give Claude a feedback loop（必做）

1. 把"检查工作"包装成单条命令：`npm test`（本项目已有，node:test 跑在临时库）。
2. 在 `CLAUDE.md` 的 Commands 里列出命令 + 健康输出示例。
3. 给可量化目标：如"所有 test/*.test.js 通过"、"接口返回 200 且带新字段"。
4. **修 bug 先写失败测试**：让 agent 先把 bug 复现成测试、跑起来确认因预期原因失败、**提交该测试**；再让 agent 在不改测试的情况下让它通过。改动前就存在的测试 = bug 已修复的证据。
5. UI 工作：给 agent 截图/浏览器工具，让它 实现→截图→对比→调整，两三轮正常。
6. **把验证纳入"完成"定义**：任务报告完成前必须跑测试并贴出输出。写进 CLAUDE.md：

   ```markdown
   ## Verifying your work
   - Test: npm test（全绿；绝不跳过或删除失败的测试）
   报告任务完成前先跑，并粘贴输出。测试失败就修代码，不要修测试。
   ```

7. **保护反馈环**：修 bug 任务期间，用 hook 阻止 agent 编辑测试文件（防止它改测试来"通过"）。

### 5.2 Continuous evals（按需引入）

AI-native 的 QA 关卡。**agent 的配置（CLAUDE.md / skills / hooks）一变，就用一组真实任务重新验证 agent 是否仍按同样标准干活。**

1. 从近期真实任务收集 20~50 个"任务 + 期望结果"（本项目从少开始：5~10 个也有效）。
2. 每个写成 eval：prompt + 可接受的检查（测试通过 / lint 干净 / 行为不变 / 遵守政策）。
3. 配置变更（CLAUDE.md/skills/hooks）后跑一遍；也可定期跑。
4. **配置变更把关**：某 skill 改动导致通过率下降 → 先评审再合入。
5. **每个生产事故转成一个 eval**，留在套件里当回归测试，防复发。

> 本项目当前无 CI：eval 可以是本地脚本（`npm run evals`），在变更配置后手动跑。

## 6. Stage 5 — Deploy：评审与门禁

**目标**：评审双向进行，agent 做到生产门禁之前，过不了门禁。

### 6.1 评审（适配单人场景）

- 单人项目没有 PR 流程，但**保留"评审"这个动作**：大改动或敏感改动（动数据库 schema、动出入库逻辑），合并/发布前自己当 reviewer 过一遍 `REVIEW.md` 定义的三类问题。
- 定义 `REVIEW.md`（repo 根）：

  ```markdown
  # Review instructions
  ## Passes（三类，每条发现标注来源）
  - Bugs: 逻辑错误、边界情况、微妙回归
  - Security: 注入、鉴权缺口、敏感数据进日志
  - Compliance: 改动符合 spec.md、plan.md、设计原则
  ## Important vs Nit
  - Important: 破坏行为、泄露数据、违反政策的发现
  - 风格和命名是 Nit
  ## 限制 Nit 数量
  - 每次评审最多报 5 条 Nit，其余汇总成计数
  ## 不报告
  - 生成文件、CI 已强制的项
  ```

- **职责分离**：写代码的 agent 不能自己批准自己。单人场景 = 你评审、你批准，但**评审动作本身不能省**，尤其是"这次改动是否偏离了 plan.md 的意图"。

### 6.2 Hooks as approval gates（本项目的门禁）

- 列出本项目必须保留的人工关卡：**改 schema.sql / db 迁移必须确认**、**`npm run seed`（破坏性）必须确认**、**发布/提交**。
- 把每个关卡表达成 hook：在 agent 行动前运行，可 allow / ask / block。
- block 时**必须说明原因和通往批准的路径**，出现在 agent 输出里。

> 单人本地工具，门禁从"提交前自动跑测试 + 破坏性命令需确认"起步即可。

### 6.3 部署（本项目 = 本地/内网发布）

- 本项目发布即 `npm run build` + 重启服务（见 README 的 deploy 脚本）。
- 原则：**agent 可以做到发布门禁之前，不能越过它**。发布命令、回滚命令应明确、排练过。
- 回滚是最该排练的路径：本项目数据在 `data/ompcb.db`（不入库），发布前备份 db 文件就是最简回滚。

## 7. Stage 6 — Maintain：闭环

**目标**：线上异常自动变成新的 `intent.md`，循环自给自足。检测保持**确定性**，agent 只在带外被触发。

### 7.1 简化闭环（本项目适用）

1. 选一个有稳定基线的指标：如 **`npm test` 通过率**、接口 5xx 率（如有）、**出入库流水一致性**（账面 = 流水，这是本项目核心不变量）。
2. 写确定性检测脚本（均值+标准差滚动窗口，或简单规则），**检测不含模型**，脚本版本化 + 有测试。
3. 分级响应（`bands.yaml` 或脚本内配置）：
   - 1σ：只记录日志
   - 2σ：只读诊断（agent 只读，不改）
   - 3σ：可行动（开 PR/触发预批准 runbook/写 intent.md）
4. agent 把诊断写成 `intent.md`（Stage 1 格式），从那里走正常管线。
5. 你（on-call）triage 队列：修 / 排期 / 忽略。**忽略会反过来调窄带，减少噪音**。
6. 修复上线后，为该 incident 加 eval（见 5.2），防复发。

### 7.2 每次踩坑的沉淀

- 发现的问题、修复过程、根因 → 写进 `docs/lessons/`（版本化 lessons 文件），未来排查可读。
- 同一个错误 agent 犯两次 → 写进 `CLAUDE.md`。
- 同一个政策被违反 → 固化成 skill + 必要时加 hook。

## 8. 治理与度量

### 8.1 控制层级速查

| 层级 | 作用 | 例子 |
|------|------|------|
| **intent/spec/plan 提交链** | 审计链：谁要求、agent 做了什么、谁批准 | git 历史 |
| **CLAUDE.md** | 上下文 + 常错点，agent 每次会话读 | repo 根 |
| **Skills** | 建议性政策，让违规变罕见 | `.claude/skills/` |
| **Hooks** | 确定性兜底，让违规几乎不可能 | `.claude/settings.json` |
| **Evals** | 配置变更的回归测试 | 本地脚本 / CI |
| **人** | 判断意图与风险，批准高风险变更 | 你 |

### 8.2 度量指标

| 阶段 | 领先指标（早期信号） | 滞后指标（结果） |
|------|---------------------|-----------------|
| Plan | 想法→intent.md 提交耗时 | intent 被接受进入设计的比例 |
| Design | intent→spec 提交耗时 | 构建开始后的需求返工（spec 在 plan 后的改动数） |
| Build | 一次实现即通过的改动占比 | 每次改动的返工轮次；diff 是否仍匹配 plan.md |
| Test | agent 改动的首次 CI/本地测试通过率 | 评审耗时；逃逸到生产的缺陷数 |
| Deploy | 首次评审耗时；无需人工触碰分支即解决的评审意见占比 | 上线前捕获 vs 逃逸生产的缺陷/漏洞 |
| Maintain | 从带异常到 intent.md 入队的时间 | 变成合并修复的发现占比；同类事故复发率 |

## 9. 落地检查清单（新功能/修复/改动走一遍）

- [ ] **Plan**：`docs/intent/<名称>.md` 已提交（问题/目标/用户/约束/未决问题）
- [ ] **Design**：`docs/specs/<名称>.md` 已提交，constraints 逐条映射，concerns 已标注 owner
- [ ] **Build**：`docs/plans/<名称>.md` 已提交（文件/顺序/风险/证明），从 plan mode 开始，未偏离计划（偏离则同提交更新 plan）
- [ ] **CLAUDE.md**：本次是否暴露了 agent 反复犯的错？是 → 已写入
- [ ] **Skills/Hooks**：本次是否涉及需强制执行的政策？是 → 已固化
- [ ] **Test**：agent 报告完成前跑过 `npm test` 并贴输出；修 bug 是先写了失败测试
- [ ] **Deploy**：涉及 schema/seed/出入库逻辑 → 已走 REVIEW.md 三类评审；破坏性操作有确认关卡
- [ ] **Maintain**：本次踩坑是否已写 `docs/lessons/`？同一错误第二次 → 已写 CLAUDE.md；是否该转成 eval？

## 10. 从哪个阶段开始（本项目的建议顺序）

| 顺序 | Play | 理由 |
