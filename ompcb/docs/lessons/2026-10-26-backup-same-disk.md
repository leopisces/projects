# Lessons: 同盘备份等于没备份（2026-10-26）

> 一句话结论：**备份与源数据共享"失效域"时，备份提供的是心理安慰，不是冗余。**
> 本文记录这个判断怎么得出、落地成什么样、以及仍然存在的缺口。

## 事故给的证据

- 2026-10-26 20:56，`C:\Users\Leopisces\Desktop\Codes\ompcb` **整个目录**被删（USN 日志确认）。
- 当时项目的备份约定是 `data/backups/` —— 它就在 `Codes\ompcb\data\` 里面。
  如果那时已有备份，会**和源库一起消失**，一份都留不下。
- 回收站里没有 ompcb 任何痕迹（62 条记录全量核对），说明是 `rm` 类硬删除：
  这类删除连"回收站"这层缓冲都不给，更别说同目录的备份了。
- 最终救回来的是 **Windows 卷影副本**（10-24、10-25 两个快照）。这属于系统还原点的副作用，
  不是项目自己的保障，而且：
  - 只覆盖 C:（D: 盘的数据没有这份运气）；
  - 有容量上限（本机 6.63 GB 上限、已用 5.21 GB），旧快照会被滚动覆盖；
  - 依赖"还原点恰好存在且晚于最后一次好数据"这个偶然条件。

## 判断法：备份的失效域三问

1. **介质是否不同？** 同一块物理盘的两个目录，磁盘损坏/分区表损坏/误格式化时同时失效。
2. **是否可能同时失效？** 同一目录树的两个子目录，`rm -rf 项目目录` 会一起带走。
3. **失效时能否自动恢复、且恢复过程不依赖坏掉的东西？** 备份要能"不靠系统还原点、不靠网络、不靠运气"被打开。

本项目原状态：三问全部不通过（同盘、同目录树、恢复依赖人记得去拷）。

## 落地成什么样（已实现）

| 维度 | 做法 |
|------|------|
| 目标 | **三写**：`data/backups`（14 份）+ `D:\ompcb-backup`（30）+ `D:\BaiduSyncdisk\ompcb-backup`（30） |
| 一致性 | 快照只生成一次（在线备份 API 合并 WAL），再复制分发，三份内容必然一致 |
| 失败语义 | 盘未挂载 → `skipped`；复制失败重试 1 次 → `failed`；**任一目标失败不影响其他目标与服务启动**；本地成功即整体成功 |
| 轮转 | 严格匹配 `^ompcb-\d{8}-\d{6}\.db$`，各目标独立份数；同步盘 `... (1)` 冲突副本只统计、不删除 |
| 可回退 | `OMPCB_BACKUP_MIRRORS=none` 关闭异地；`OMPCB_BACKUP_KEEP` 调本地份数 |
| 可观测 | `npm run backup:status`：逐目标份数 / 最近成功时间 / 占用 / 冲突副本数 |

成本核对：单份 ≈ 220 KB，30 份 ≈ 6.6 MB。D 盘剩余 458 GB —— 冗余的边际成本几乎为零，
而"没备份"的代价是这次丢掉的 11 天数据。

## 仍然存在的缺口（诚实记录）

1. `D:\ompcb-backup` 与 `D:\BaiduSyncdisk\ompcb-backup` **在同一块物理盘（D:）**，
   严格说只有百度云端那份是"真异地"。真正的第二块盘需要插移动硬盘后改一行
   `OMPCB_BACKUP_MIRRORS`。
2. 备份是**滚动窗口**（14/30 份），不是版本历史；误操作后写入的新数据会逐渐顶掉旧份。
   如果要防"数据被改坏"，需要增量/WAL 归档，那是另一个量级的改动。
3. 备份**未经恢复演练**：目前只验证了"文件能打开且 `quick_check` 通过"，
   没做过"从备份完整还原到临时目录再用 UI 跑一遍"。
   建议每季度做一次恢复演练（见下）。

## 恢复演练检查单（建议每季度一次）

1. `npm run backup:status` 确认最新一份时间合理。
2. 停服务：`Stop-ScheduledTask -TaskName OMPCB`。
3. 把最新备份**复制**到临时目录（不要直接覆盖生产库），用
   `node -e "new (require('better-sqlite3'))('临时路径')"` 或 `sqlite3` 打开，`PRAGMA quick_check`。
4. 核对行数：`materials` / `inventory` / `inventory_log` 与生产库一致。
5. 结束，生产库不动（演练只读）。
