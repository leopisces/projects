# Intent: 备份不跟源库同盘——加异地副本

Author: leopisces. Status: draft.
日期: 2026-10-26

## Problem

- 现在的备份默认落在 `data/backups/`，与源库 `data/ompcb.db` **在同一块盘（C:）同一个目录树**。
- 今晚的事故就是最直接的反例：`Codes\ompcb` 整个目录被删除，如果当时 `data\backups` 在里面，
  备份会和源库一起消失。这次能救回来靠的是 Windows 卷影副本（系统还原点），属于运气 + 副作用机制，
  不是项目自己的保障。
- 整盘损坏、BitLocker 异常、误格式化 C: 等场景下，同盘备份等于没有备份。
- 卷影副本只覆盖 C:，且有容量上限（当前 6.63 GB 上限、已用 5.21 GB），会被滚动覆盖掉。

## Proposed outcome

- 每次备份**至少产生一份落在另一块物理盘（D:）的副本**。
- 可选再落一份到同步盘目录（`D:\BaiduSyncdisk\...`），获得云端的异地副本。
- 本地主副本仍然保留，恢复时走本地快速路径，不依赖网络。
- **任一路径失败不影响其他路径，也不影响服务启动**（fail-open + 告警）。
- 每个目标目录独立轮转，空间上限明确、可配置。
- 备份/恢复流程在 README 里能被人照着做完，不需要读源码。

## Affected users and systems

- 用户：单人自用，唯一使用者（本项目作者）。
- 文件/目录：`data/backups/`（本地主副本）、`D:\ompcb-backup\`（异地副本，名字待定）、
  可选 `D:\BaiduSyncdisk\ompcb-backup\`（云同步）。
- 代码：`scripts/backup-db.mjs`（单目标 → 多目标）、`scripts/install-backup-task.ps1`、
  `scripts/serve.ps1`（启动兜底）、`README.md` / `CLAUDE.md` / `AGENTS.md`（口径）。
- 不涉及：业务表结构、`/api/*`、Vue 前端、`inventory_log` 统计口径。

## Constraints

- **不能**因为 D 盘未挂载、同步盘目录不存在、网络慢，就让备份失败或让服务起不来。
  失败只告警，并按"至少本地成功即算成功"的口径对外报告。
- 不改变源库路径（`OMPCB_DB` 口径不变）与备份文件命名规则（`ompcb-YYYYMMDD-HHmmss.db`）。
- 不引入新依赖：仍然只用 `better-sqlite3` + Node 标准库。
- 各目标的保留份数必须**独立可配**（本地和异地的容量/价值不一样）。
- 备份产物不进 git。
- 同步盘客户端可能给文件改名/加后缀（如 `ompcb-xxx (1).db`）、产生临时文件（`.btsync`、`~$*`），
  轮转逻辑必须容错，不能误删用户文件。
- 单次备份耗时不能显著增加（当前单份 ≈ 225 KB / WAL 合并后 4 MB 级，本地拷贝是毫秒级）。

## Open questions

1. **异地目标选哪个**：`D:\ompcb-backup`（纯本地第二块盘）、`D:\BaiduSyncdisk\ompcb-backup`
   （百度同步盘，云端异地），还是两个都写？
2. **C 盘本地副本还留不留**：双写（本地快 + 异地稳）还是只写异地（省空间）？
3. **各自保留多少份**：建议本地 14 份、异地 30 份（异地更稀疏、更有价值），是否认可？
4. **同步盘容错口径**：轮转时是否严格只认 `^ompcb-\d{8}-\d{6}\.db$`（我倾向严格），
   同步冲突产生的 ` (1)` 后缀副本要不要一并清理？
5. **离线检测**：D 盘未挂载 / 目录不可写时，是"跳过并告警"还是"退回只写本地"？（两者体验接近，需定口径）
6. **备份状态可见性**：要不要在 README 里给一条命令（如 `npm run backup:status`）查看
   各目标最近一次成功时间与占用空间？
7. **恢复流程放哪**：`REVIEW.md` 已有回滚预案，`README` 是否再写一份面向"我明天忘了"的短版？

## 范围外（明确不做）

- 云对象存储备份（S3 / OSS / WebDAV）与加密上传。
- 增量备份 / WAL 归档 / 时间点恢复（PITR）。
- 自动把备份同步到另一台机器。
- 备份状态的 Web UI。
